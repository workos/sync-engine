Postgres Sync

A sync engine that mirrors WorkOS data into a customer's own Postgres, so identity data can be joined to their application data in SQL. Working prototype, tested against our production API.

Working prototype 92 tests passing Verified against live API MIT · TypeScript

01The question customers can't answer

Every application built on WorkOS eventually needs to ask something that spans two systems.

  • Which enterprise seats have we provisioned that nobody uses?
  • Which organizations verified a domain and then never finished setting up SCIM?
  • Which accounts saw a spike in failed sign-ins last night?

None of these have an endpoint. Each is a join between data in WorkOS and data in the customer's database, and answering it through an API means paginating one list, holding it in memory, paginating another, and reconciling the two in application code.

Customers do build this. It starts as a webhook handler that writes a users table, then grows a backfill script, then a nightly repair job, then a second table — and at no point does anyone feel confident it is correct. We know the shape of that code because our own docs describe it, and then leave the implementation as an exercise.

The gap is specific. We publish the argument for the Events API over webhooks, the conditional-upsert pattern, and a data-reconciliation guide that says drift detection “requires performing diffs to identify deletions… making it essential to carefully design and test the reconciliation process.”

Then we stop. Every customer writes that reconciler themselves, and most of them skip it.

02What it is

An open-source library plus a CLI. It creates a workos schema in the customer's database, loads what already exists, then follows the Events API to stay current.

Three subsystems, and all three are required. This is the part that makes the hand-rolled version harder than it looks.

Backfill

Pages the REST list endpoints. Events are retained 90 days — everything older exists only here. This is what a webhook-only integration structurally cannot do.

Tail

Polls the Events API from a durable cursor. Ordered, replayable, paced by the consumer. No public endpoint to expose.

Reconcile

Diffs the mirror against the API. The only thing that finds a missed delete — a deleted object is absent from every list endpoint, so re-listing can never reveal it.

It mirrors users, organizations, memberships, domains, invitations and sessions; directories, directory users and groups; SSO connections; roles, permissions and feature flags. Every event is archived alongside them.

One stream is worth calling out. The fifteen authentication.* event types have no REST endpoint anywhere in our API. There is no way to list sign-ins. If a customer does not capture them as they happen, that history is gone after 90 days. Mirroring turns it into an ordinary table — “which accounts had five failed sign-ins in the last hour” becomes a GROUP BY.

03The API

Same engine in three packagings: a library, a CLI, and a container. The library form is the one that matters — for the Stripe engine it out-installed the modular alternative five to one.

Command line

CommandDoes
initCreates the schema. Fingerprinted, so re-running is a no-op.
backfill [--resume]Pages every list endpoint. Checkpoints per page.
listenPolls the Events API forever. Handles SIGTERM mid-batch.
reconcile [--repair]ID-set diff against the API. Exits 2 on drift, so it works as a scheduled check.
refreshRe-lists to repopulate fields event payloads omit.
statusCursor age, per-stream freshness and lag.
redact --user <id>Hard-deletes one subject from the mirror and the event archive.

Library

Webhooks are supported, but as a trigger rather than a source of truth: a verified delivery wakes the poller early, and state still flows through the ordered stream, so you keep ordering and replay.

Mirroring several environments

One API key is one environment is one cursor. A workspace can hold dozens, and environment names repeat across projects, so the customer supplies a stable label that is written to every row as _env and forms part of every primary key.

04The schema

_raw is the only column the engine ever writes. Every typed column is generated from it — including the primary key.

A field added to our API can never break ingest. It is queryable as _raw->>'field' the moment it appears, and promoting it to a typed column is pure DDL — STORED computes it from rows already present, so there is no backfill and no downtime.

No foreign keys. Events routinely arrive with children before parents — a group.user_added can land before the user.created it references. An FK converts that ordering artifact into a hard write failure and a stuck stream. The original Stripe engine shipped FKs, collected bug reports for years, and eventually dropped all of them in one migration.

One Postgres constraint worth knowing

Postgres rejects (_raw->>'created_at')::timestamptz in a generated column: casting text to timestamptz depends on the session's DateStyle and TimeZone, so it is not immutable. Stripe's engine never hits this because Stripe serializes times as Unix integers. We use ISO-8601 strings, so it hits us immediately.

The engine installs a parser built only from immutable primitives — regexp_match, make_timestamp, timezone('UTC', …), make_interval. It handles fractional seconds, bare Z, and numeric offsets, and returns NULL rather than raising on anything it cannot parse, because a generated column that throws rejects the whole row and poisons the batch.

05The hard parts

Each of these is a documented failure in a comparable engine. They are the reason this is worth productizing rather than leaving to a cron script.

Out-of-order delivery

Every write is gated on a source-derived timestamp:

It is >= rather than > deliberately. Two events can carry the same timestamp, and with a strict comparison the second is dropped permanently — which is exactly how the Stripe engine kept showing subscriptions as “trialing” after they converted. Ties resolve last-writer-wins, and reconciliation is the backstop rather than the comparison.

The timestamp is synthesized in the ingest layer and never by the database. A trigger stamping now() records when you wrote, which is not comparable across delivery paths — and worse, a redelivered event would always look newer than the row it replaces, defeating the gate entirely.

Our event payloads are subsets of our objects

This is the most consequential WorkOS-specific behaviour, and it is the one I would most like a second opinion on.

EventFields the REST object has and the event does not
user.*external_id, metadata, last_sign_in_at, locale
organization.*metadata, stripe_customer_id, allow_profiles_outside_organization
organization_membership.*organization_name, directory_managed, embedded user
role.*id, name, description, resource_type_slug
dsync.user.*groups (explicitly omitted for performance)

A naive implementation replaces the row on every event and silently nulls out external_id — the exact column customers join on. So event writes shallow-merge into _raw, REST writes replace it, and hydration can re-fetch on create. Three mechanisms to work around one payload shape.

Worth asking as a platform question rather than a sync-engine question: should user.updated just carry the full object?

Deletes

Tombstoned, not removed — _deleted_at is set and the last known payload is kept, because it is the only remaining record of what was deleted. Deletes are not staleness-gated, and _deleted_at is never cleared: a late updated event refreshes the payload but must not resurrect the row. Our IDs are ULIDs and never reused, so that is safe. Memberships are the exception, since a re-add is a genuine event.

Reconciliation

Three tiers on three cadences: continuous freshness, daily counts, weekly ID-set diff. The diff reports two numbers per stream, and they mean different things — rows present locally but not upstream are missed deletes, rows upstream but not local are missed creates.

06What building this found in our own API

The prototype passed 89 tests against a fake before it ever touched production. First contact with the real API broke it three times. All three are documentation or design issues on our side, and I think they are the most useful part of this document.

Finding 01 · spec is wrong

events is required, not optional

The published OpenAPI spec marks the events filter required: false. The live endpoint disagrees:

GET /events?limit=100
400 {"message":"One or more event names (e.g. dsync.user.created) must be
     provided using the events parameter.","code":"invalid_events_request"}

The Node SDK types the field as required, which reads like a generator artifact until you test it — the SDK is right and the spec is wrong. I validated all 63 catalog event names individually; unknown names are rejected the same way.

Why it matters beyond a typo A consumer cannot subscribe to “everything.” It must enumerate event types, which means a newly shipped WorkOS event type does not reach any customer's sync until they update and redeploy. That is a real coupling between our release cadence and theirs, and it is currently undocumented.
Finding 02 · silent correctness trap

order has no effect, and order=desc&limit=1 returns the oldest event

order=asc, order=desc, and omitting the parameter return byte-identical pages, always oldest-first. The documented default of desc is not observable.

order=asc   → event_01KZCAQTRM…  20:02:53Z   (oldest)
order=desc  → event_01KZCAQTRM…  20:02:53Z   (identical)
(omitted)   → event_01KZCAQTRM…  20:02:53Z   (identical)

The natural way to record “start from now” before a backfill is to ask for the newest event id with order=desc&limit=1. That returns the oldest event instead, so the cursor lands at the beginning of the retention window and the tail replays 90 days on every fresh start.

Why it matters Nothing errors. Writes are idempotent, so the mirror still converges — it just does a full replay while looking healthy. Our own docs describe cursors in terms of “the ID of the latest processed event,” which is the assumption that breaks. The fix is to record a timestamp and bootstrap with range_start, then switch to after.
Finding 03 · confirmed by testing

Event payloads really are subsets, in production

Verified end to end: a live user.updated for a user with external_id and metadata set carries neither. A whole-row upsert nulls both. This is documented, but the consequence — that the field customers use as their join key disappears on every update — is not.

Also confirmed range_start and after are mutually exclusive and enforced (400 "Only one of range_start and after may be provided."), and range_start=<now> correctly returns zero events.

Independent of whether we ship a sync engine, these are worth fixing: correct the spec, document the ordering behaviour, and decide whether enumerated subscriptions are the contract we want.

Read-only, against an environment with real data

Backfilled 11 users, 3 organizations, 5 memberships, 4 domains, 6 directory users through a live SCIM directory, a GenericSAML connection, 2 roles and 9 permissions. Every real ISO-8601 timestamp parsed through the generated column, none null. Reconcile reported zero drift on all 11 streams, and a second backfill created nothing.

Full cycle, against a disposable environment

The most convincing result was one I did not stage. Reconcile flagged a connections row the API did not have. It came from a real connection.activated event in that environment's history, for a connection that no longer exists. Backfill found zero connections; the event replay created one; no future event would ever correct it.

That is the missed-delete case occurring naturally in production data — the one failure mode only a set difference can catch. My test asserted zero drift there. The assertion was wrong; the engine was right.

Tests run against PGlite — real Postgres compiled to WebAssembly — so they exercise actual generated columns, xmax, jsonb operators and immutability rules, with no Docker and no setup. The fake API reproduces the behaviours that make syncing hard: subset payloads, out-of-order and duplicate delivery, rate limiting, and deletes that vanish from list endpoints.

08Where I want you to push back

These are the decisions I am least sure about. Arguments welcome, especially on the first three.

Should this be first-party at all?

The Stripe path was community-first, then adoption. Starting first-party skips a step but commits us to API surface we might want to change. The counter-argument: shipping it ourselves is what makes the Events API's guarantees real rather than aspirational.

Does this cannibalize anything?

A customer with a local mirror makes fewer API calls, and their read path no longer depends on us being up. I think that is a feature and a trust argument — a continuously synced mirror is also an exit hatch, which defuses the lock-in objection that drives migrations away. But it is worth someone arguing the other side.

Is a read model enough, or will people demand write-back?

The sync is one-directional and I want to keep it that way. Sequin — the team who tried hardest at this — ended up writing a Postgres wire-protocol proxy to make synchronous write-through work, then de-prioritized the feature. Saying no is easy now and hard later.

Should we fix the payload asymmetry instead of working around it?

Three mechanisms exist in this engine solely because user.updated omits external_id and metadata. Making event payloads match the objects would delete all three. That is a platform change with its own costs, but it would improve every hand-rolled integration too, not just this one.

Coverage: where should the line be?

Currently 14 tables across identity, directory, SSO and RBAC. Audit logs are deliberately excluded — they have their own export and streaming products. FGA is poll-only because it emits no events at all. Both are defensible and both are arguable.

Distribution

The Stripe engine sat at ~400 downloads/month for six months as “a library plus a blog post,” then jumped to 56.8k the month a one-click dashboard integration shipped. Neither its launch nor its transfer to Stripe produced any HN discussion. If that pattern holds, the lever here is a setup path in the dashboard, not a launch post.

Known limitations, stated plainly

  • Sessions are only listable per user and only while active, so backfill is partial by construction.
  • There is no dsync.updated event, so a directory going linked → invalid_credentials emits nothing. Only reconcile sees it.
  • SSO profiles cannot be mirrored at all — no list, no get, no events.
  • The mirror is eventually consistent. It is a read model, not a system of record: authorization decisions belong on the session token, and a just-created user should be read from the API response you already have.

09The bet

Sequin's published wishlist for a “syncable API” — an ordered, replayable, cursor-paginated change feed with historical backfill — is a description of the Events API we already shipped.

Stripe's ecosystem had to reverse-engineer that around a 30-day event window and an endpoint that silently skipped events. We offer 90 days and documented ordering guarantees. The primitive is in place and, as far as I can tell, unexploited: nobody is building on it, and the customers who need it are hand-rolling a worse version.

The narrow read of this proposal is a library that saves customers a week of work. The wider read is that Stripe went OSS engine → one-click integration → Stripe Database, a managed hosted Postgres of your data, in about eighteen months. If that ladder is the right shape, this is the first rung, and the last rung is a product.

What I would like from this document is disagreement about which rung is worth standing on.
